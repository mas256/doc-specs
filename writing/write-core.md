# 文書作成規格 第4版 書く手順 core(全工程共通)

あなたは、依頼者と議論しながら文書を作る。作業は工程0〜4に分かれ、工程ごとに従うファイルが決まっている(W2)。どの工程でも、先に common.md を読む。工程1と工程4では、handoff.md(author-style の枠、レビューとの受け渡し、記録の置き場所)も読む。この規格で判断できない事項は推測で補わず、依頼者に質問する(依頼者と話せない担当は、窓口へ返す。W2.9)。

書く手順(writing/)は、文書を書き、書き直す。書いた本文の評価はしない。評価は、レビューの手順(review/)の担当が行う。この規格の中で「この規格」と言うときは、書く手順を指す。

## W0 記法

- W0.1 記法は common.md の N0 に従う。
- W0.2 この規格の規則IDの接頭辞は、W=core、Z=工程0(壁打ち)、R=工程1(要件定義)、O=工程2(草案)、M=工程3(執筆)、E=工程4(改稿)、Y=文体と書き方の型。N で始まるIDは common.md、AR・AP・AD で始まるIDは author-style.md を指す。

## W1 役割

| 役割 | 担うこと |
| --- | --- |
| 依頼者 | 何を書くか、何を伝えるか、どこまで詳しく書くか、何を強調するかを決める。成果物を承認する |
| AI | 聞き出す、批評する、案を出す、整理する、本文を書く。内容の採否は決めない |

- W1.1 AIが出したものの扱いは、承認の関門(common.md N7.5)に従う。案ごとに「AI提案」と印を付けることはしない。依頼者が承認したものだけを成果物に入れる。
- W1.2 依頼者の考えが定まっていない事項を、AIの案で埋めて先へ進まない。未決のまま記録し、質問する。
- W1.3 詳しさ、強調、式や図で示すかどうかは、依頼者が決める。AIは理由を添えて提案してよい。

## W2 工程と成果物

| 工程 | 行うこと | 成果物 | 従うファイル |
| --- | --- | --- | --- |
| 0 壁打ち(目的)(任意) | 誰に何を伝えたいかが固まっていない段階で、論点を広げ、材料を集める | 壁打ちメモ | core、phase-0-discussion.md(Z1〜Z4) |
| 1 要件定義 | 議論によって、想定読者、読後に期待すること、必ず扱いたい内容、制約を確定する | 要件定義書、author-style.md | core、phase-1-requirements.md、style-presets.md |
| 0 壁打ち(中身)(任意) | 題材・切り口・主張の核を広げ、誤りと反論を確かめ、依頼者の取捨を受ける | 取捨の承認を受けた中身 | core、phase-0-discussion.md(Z5) |
| 2 草案 | 箇条書きの構成案を、依頼者と共同で作る | 構成案、用語・表記表への追記案 | core、phase-2-outline.md |
| 3 執筆 | 構成案に基づいて本文を書く | 本文、引き渡しメモ | core、phase-3-writing.md |
| 4 改稿 | レビューで採用された指摘と方針に基づいて、本文を書き直す | 本文、変更記録 | core、phase-3-writing.md、phase-4-revision.md |

- W2.1 流れの正本は common.md N6 である。工程1〜3は1から順に進める。壁打ち(目的)は、誰に何を伝えたいかがまだ決まっていない場合に工程1の前に行い、壁打ち(中身)は、題材・切り口・主張の核が決まっていない場合に工程1と工程2の間で行う(どちらも、依頼者が不要と言えば行わない)。工程4は、レビューの項目一覧と採否表(N5.2)が渡されたときに行う。工程1、壁打ち(中身)、工程2では、成果物を示して承認を明示的に求め、依頼者が承認するまで次へ進まない。壁打ち(目的)には承認を設けない(Z4)。工程3の本文は、依頼者が確かめた後、レビューへ進む(common.md N6.2)。
- W2.2 ファイルを選んで読める環境では、その工程のファイルだけを読む。先の工程のファイルを先に読まない。
- W2.3 承認された成果物は、次の工程の正本である。後の工程で内容・順序・詳しさの変更が必要になった場合は、先に元の成果物を改め、承認を得てから続ける。ただし、表現だけの変更は本文だけを直してよい。author-style.md は書き手の正本であり、AIは書き換えない。変える必要がある場合は、追記案を示して依頼者に決めてもらう(N3.7)。
- W2.4 途中から始める場合:依頼者が要件定義書や構成案に当たるものを持ち込んだ場合は、その工程の書式(R4、O4)に照らして欠けている項目だけを確かめ、承認を得て次の工程へ進む。
- W2.5 小さい文書:本文が数段落に収まる文書では、要件定義書、壁打ち(中身)の取捨、構成案を一つにまとめ、一度の承認で工程3へ進んでよい(common.md N6.2)。ただし、R4の必須項目と構成案は省かない。
- W2.6 大きい文書:複数の章を持つ文書では、工程2と工程3を章ごとに繰り返してよい。その場合は、文書全体の構成(章の一覧と、各章が読者に起こす変化)を先に構成案にして承認を得る。
- W2.7 author-style:渡されている場合は、それを使い、工程1では未記入の欄だけを尋ねる。渡されていない場合は、工程1でテンプレートに沿って作る(R3)。工程1を経ずに工程3・4から始める場面で、渡されていないか、未記入の欄がある場合は、窓口が N4.3・N4.4 に従って依頼者に尋ねる(第3部の固定する用語と第4部は、未記入のままでよい)。執筆と改稿の担当は聞き取りをしない。担当が受け取った author-style の未記入の欄は、その事項に定めがないものとして扱う(N4.6)。
- W2.8 この規格で書かれていない既存の原稿を改稿する場合:要件定義書は必須とする。レビューのLeadが書き出した依頼内容ファイル(N5.1。records/brief.md)がある場合は、それを要件定義書として使い、必須の2項目(第2項と第3項)が「未定」や「原稿のとおり」でないことだけを確かめる。ない場合は、phase-1-requirements.md を読み、原稿から起こして、必須の2項目を確かめ、承認を得る。構成案は、構成を変える修正(規模が大)の対象範囲についてだけ作る。規模が小の修正だけなら、構成案は作らない。
- W2.9 窓口・指示役・担当(common.md N7):依頼者との対話(壁打ち、要件定義、草案)は窓口が行う。サブエージェントを使える環境では、壁打ち(中身)の候補出しと確かめを担当に任せる(Z5.3)。サブエージェントを使える環境では、工程3と工程4の本文を書く作業を、工程0〜2の議論を見ていない担当(執筆の担当、改稿の担当)に任せ、指示役が起動する。一つの会話で窓口と指示役を兼ねてよい。
  - 担当に渡すのは、common.md、core、その工程のファイル、要件定義書、構成案、author-style.md、素材(工程4では、加えて handoff.md、phase-3-writing.md、項目一覧と採否表の該当行、対象の本文)だけにする。議論の経過や要約、壁打ちメモは渡さない。
  - 担当は、依頼者に直接尋ねない。質問、【要確認】、確かめられなかった事実は、窓口への返信に書いて返す。窓口が依頼者に取り次ぐ。
  - 依頼者の答えを得たら、窓口は同じ種類の担当を起動し直し、書きかけの本文(その版)と答えを渡して、該当箇所だけを直させる。サブエージェントを使える環境では、窓口は本文を自分で直さない(本文を書いた者は、その本文の評価者になれない。review/core.md C1.3)。【要確認】が残る本文は、レビューへ進めない。
  - 工程4で窓口が担うのは、採否の確認(E1.2)、選択肢の確認(E3.6)、規模が大の範囲の構成案の改訂と承認(E2.2)である。これらを済ませてから、改稿の担当を起動する。
  - 長い文書では、執筆の担当と改稿の担当を、章ごとに起動してよい。渡すのは、その章に関わるものだけにする。改稿では、章ごとの変更記録を、指示役が一つにまとめる。章ごとの担当が同じファイルを同時に直すことはしない。本文が章ごとのファイルに分かれていれば並べて起動してよく、一つのファイルなら順に起動する。
  - サブエージェントを使えない環境では、同じ会話で続けてよい。その場合も、根拠にするのは承認済みの成果物だけである(M1.1)。
- W2.10 モデルは、担当の定義ファイル(agents/)に従う(最大は sonnet の high。common.md N12)。執筆の担当は sonnet の high、改稿の担当は方針どおりに直すので sonnet の medium を出発点にする。依頼者との対話(壁打ち、要件定義、草案)は窓口が行い、分けない。壁打ち(中身)の担当のモデルは Z5.3 に従う。
- W2.11 外部の資料に当たる作業:執筆と改稿の担当は、検索の手段を持たない。確かめられなかった事実・数値・引用は「未確認」として返す(M5.2、E5.3)。窓口は、それらを確かめる事項の一覧(事項ごとに番号、確かめたい事柄、該当箇所)にまとめ、レビューの手順の検証担当(agents/review-checker)を、作業種別「書く側の要求つき」(U1.4)で起動して確かめさせてよい。壁打ち(中身)の題材も、同じ形で確かめさせる。結果は依頼者に示し、本文への反映は工程3・4の手順で行う。壁打ち(目的)の下調べ(Z3)は、窓口が自分で行ってよい。壁打ち(中身)の題材の誤りは、窓口が自分で済ませず、検証担当に確かめさせる(Z5.1 の4)。
- W2.12 作業パケット(書く側。common.md N12.3):担当を起動するときは、次の項目をすべて書く。一つでも欠けたパケットで担当を起動しない。パケットは records/work/ に置く(handoff.md N5.4)。
  1. 共通:担当の種類と段、規格フォルダの場所、読むファイルの場所(要件定義書、author-style.md、構成案、素材のうち、その担当に渡すもの。W2.9)、範囲(章・節。全体なら「全体」)、書き出し先のファイル名、止まる条件(担当の手順に書かれた質問・【要確認】の扱い)、返す形(担当の手順の返却の節)。
  2. 執筆:書く本文の版の名(handoff.md N5.4)。
  3. 改稿:項目一覧と採否表の該当行、変更前の版の場所、変更後の版の名、変更記録の書き出し先。
  4. 壁打ち(中身):段(観点/題材/切り口/ロールモデル)、数(Z5.1、Z5.2)、前の段の結果(題材の段では観点の一覧、切り口の段では題材の一覧、ロールモデルの段では候補)、切り口の段では依頼者が持ち込んだ視点、ロールモデルの段ではロールモデルの人物像そのもの(要件定義書が名前だけを書いている場合は、テンプレートから写す)。
  5. 検証担当(書く側の要求つき。W2.11):作業種別「書く側の要求つき」、確かめる事項の一覧。

## W3 用語

共通の用語(想定読者、変化、単位と粒度、負担、飛躍、脇道、争点、判断上の仮定、著者規則、固定語、表記ゆれ、用語ゆれ、言い換え、方針、理解上のまとまり、歩幅を合わせる文、読後に期待すること、到達点、省略、反論、構成案、観点・題材・切り口、制約、言い回しのゆれ)と、役割(窓口、指示役、担当)は、common.md の N1 と N7 に定めがある。

## W4 判断の原則

判断の原則は common.md の N8 に移した(第4版)。番号は対応している(W4.1〜W4.6 → common.md N8.1〜N8.6)。

## W5 議論の進め方

- W5.1 質問するのは、回答によって成果物の内容・構成・書き方が変わる事項だけにする。依頼文・資料・これまでの回答で答えられている事項を質問しない。
- W5.2 質問は、できる限り1回の発言にまとめ、重要な順に並べる。ただし、まとめるために質問を作らない。選べる事項には、選択肢と、AIが勧める案とその理由を添える。往復の回数に上限は設けない。
- W5.3 批評:依頼者の案(構想・箇条書き・構成)には、良い点、悪い点、改善案を、それぞれ根拠を添えて一度にまとめて返す。悪い点は、想定読者にどんな支障が出るかで述べる。
- W5.4 依頼者の案を、断りなく書き換えた版で置き換えない。変える場合は、どこをなぜ変えたかを示す。
- W5.5 未決事項:争点は、その場で質問し、回答を得るまで、その事項に依存する作業を進めない。争点でない未決事項は、解釈を一つ選び、判断上の仮定として成果物に記録して進める。
- W5.6 決まったことは成果物に書く。発言のたびに、それまでの決定を繰り返し要約しない。

## W6 考える量と書く量

- W6.1 検討の過程は出力しない(common.md N8.9)。
- W6.2 成果物は、ファイルを書ける環境ではファイルとして、そうでなければ独立したブロックとして示し、会話の文と混ぜない。

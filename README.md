# 文書作成規格 第5版(人間向け)

作成日:2026-11-11。この文書はAIに渡さなくてよい。

## 構成

```text
START.md                  AIが最初に読む入口(依頼の種類と、読むファイルの表)
common.md                 全担当が最初に読む core(方針、用語、流れ、役割、判断の原則、品質の基準、モデル)
handoff.md                受け渡しの書式と記録の置き場所(要件定義書の七つの欄など)
author-style-template.md  author-style のテンプレート(事項ごとの問いつき)
writing/                  書く手順(core、壁打ち、論点案の作成、構成案の作成、執筆、読んで直す)
review/                   形式のレビューの手順(第4版の定めの写し base-v4.md、改稿 revision.md、core、役割ファイル)
agents/                   サブエージェントの定義(モデルと effort を含む)
parts/                    部品(読者層や文書の種類ごとの選ぶ基準。形は後で決める)
DESIGN.md                 設計思想(人間と、指示書を改めるAIが読む)
MANUAL.md                 利用者向けマニュアル(章立てだけ)
```

author-style.md は、この規格群に含まれない。依頼者が持つ。壁打ちを終えた後に、議論に準拠してAIが作り、依頼者が承認する。「未決」の欄が残っていても使える(その事項は定めがないものとして扱われる)。

## 置き方

ふつうの会話(無料版を含む)で使える。サブエージェントは要らない。

1. 作業フォルダを決める(標準は GitHub のリポジトリか Google Drive のフォルダ)。この指示書のフォルダも、そこかプロジェクトに置く。
2. 会話のはじめに、START.md と、AIが読めと言うファイルを渡す。AIは、変えたファイルを丸ごと、あなたが選んだ形(テキストか md)で返すので、作業フォルダに保存する。
3. 記録は records/current.md(台帳)に一本化されている。次の会話では、台帳と要るファイルを渡す。
4. Claude Code や Codex では、最初にサブエージェントを使うかを聞かれる。Claude Code では、`agents/` の11ファイルを `.claude/agents/` に写す。指定しなければ、主の会話が担当になりきる。

## 始め方

主の会話に `START.md` を読ませ、したいことを伝える。

| したいこと | 伝えること |
| --- | --- |
| 文書を作る | 作りたい文書のイメージ。決まっていなくてよい。AIが壁打ちを始め、あなたが「終える」と言うまで議論する |
| 原稿を読んで直す | 原稿と、読者・目的 |

どれぐらいAIに任せるかは、最初に聞かれる。全部任せることも、自分で書いてAIに読んでもらうことも、その間もできる。途中で変えてよい。
| 形式のレビュー・改稿・再検証 | 第4版と同じ(review/) |

## 1周の流れ

流れの正本は common.md の N6 にある。以下は人間向けの要約である。

1. 壁打ち:AIと議論する。AIは広く調べ、切り口(着眼点・主張・主な題材)の案を複数出す。あなたが切り口を決め、「終える」と言うと、AIが要件定義書と author-style を作る。承認する。
2. 論点案の作成:選んだ切り口を補強する題材の案が、事実の確かめと読者から見た読みを添えて返る。選んで承認する。
3. 構成案の作成:並べ方の案が2〜3(小さい文書は1)返る。段落ごとに何を言うかが一行ずつ書かれている。選び、決めたい欄だけ決めて承認する(決めない欄は「任せる」)。
4. 執筆:自分で書くか、AIの下書きに手を入れるか(段落ごとに分けてもよい)。
5. 読んで直す:AIが読者として読み、弱いところを影響の大きい順に返す。どれを直すか、どこへ戻るか、誰が直すかを決める。

## モデルと effort

| 担当 | 定義ファイル | モデル | effort |
| --- | --- | --- | --- |
| 窓口(壁打ちの相手。Lead を含む。主の会話) | なし | sonnet | high |
| 照合担当 | review-collator | haiku | medium |
| 構造担当 | review-structure | sonnet | high |
| 章担当 | review-chapter | sonnet | high |
| 検証担当 | review-checker | sonnet | high |
| 確認者 | review-verifier | sonnet | medium |
| UI担当(媒体の確認を指示した回だけ) | review-ui | sonnet | medium |
| 削る案(削る手順のときだけ) | writing-cutter | sonnet | high |
| 企画(論点案と構成案) | writing-planner | sonnet | high |
| ロールモデル(論点案、読んで直す) | writing-rolemodel | sonnet | medium |
| 執筆(下書き) | writing-writer | sonnet | high |
| 改稿(読んで直す、採否表) | writing-reviser | sonnet | medium |

- 方針(2026-11-16):最終目標は、sonnet と haiku だけで回せること。sonnet の high を最大とし、性能のそこまで要らない担当は sonnet の medium、haiku の high・medium に下げる。opus は指示書を作り直す段階でだけ使う。
- 道具は、担当の仕事に要るものだけを定義ファイルの tools に書く(書いていない道具は使えない。試行で、汎用の担当が指示にない操作を試みたため)。シェル(Bash)を持つのは、検索とスクリプトで抽出・差分を取る照合担当、再計算をする検証担当、差分を確かめる確認者、表示を書き出す UI担当だけである。

- 要約テスト(review/role-lead.md の L3.11)は、定義ファイルを持たない。起動のしかたは L3.11 にある。
- 検索の道具(WebSearch、WebFetch)は、照合担当を除くすべての担当が持つ。使うのは事実の確かめと視点を増やすためだけで、答え(結論、本文の文面、構成)を得るためには調べない(依頼者の決定、2026-11-19)。
- 章担当は人数が最も多く、使用量を支配する。設定を見直すときは、review/rationale.md の実験の手順で比べる。
- 結果が足りないときは、common.md N12.1 に従う(モデルを上げず、作業パケットと指示書の書き方を見直す)。
- 環境変数 `CLAUDE_CODE_EFFORT_LEVEL` を設定していると、定義ファイルの effort より優先される。

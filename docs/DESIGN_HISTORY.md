# doc-specs 設計思想と改訂の経緯（フラグシップモデル・仕様改訂AI向け）

対象リポジトリ: [mas256/doc-specs](https://github.com/mas256/doc-specs)

この文書は、文書作成規格（第5版および今後の改訂案）の背後にある**設計思想・過去の試行錯誤・撤回したルールの理由**をまとめたものです。特にフラグシップモデル（`Opus` クラス等）が高度な判断を行う際や、指示書自体を改訂する際に、**過去に害が出た制約を良かれと思って復活させてしまう「先祖返り」を防ぐこと**を目的としています。

※ 日常の文書作成で軽量モデル（`Sonnet` / `Haiku`）にそのまま渡す用途には使いません。

## 1. 核となる5つの基本方針

[DESIGN.md](https://github.com/mas256/doc-specs/blob/main/DESIGN.md) および [common.md](https://github.com/mas256/doc-specs/blob/main/common.md) を貫く設計の芯は次の5点です。

0. **作り手は依頼者**: AIは材料・選択肢・ドラフトを出す伴走者であり、依頼者が「任せる」と明示した部分だけ推奨案で進める。

1. **厳密と自由を場所で分ける**: 依頼者が決めた仕様（読者・読後に期待すること・立場・制約・`author-style`）は厳密に守り、着眼点・題材・構成・日本語表現はAIを縛りすぎず自由に広げさせる。

2. **広げて選ぶ**: 論点も骨格も文体も、AIが1案で決め打ちせず複数の候補を並べ、人間が選んで確定する。

3. **依頼者の思考をなぞる**: 「決める → 出す → 並べる → 書く → 読んで直す」の順で進め、問題が起きれば性質に応じて前の段階へ戻る。

4. **単純に始め、失敗が見えたときだけ足す**: 思いつきで予防的ルールを増やさず、実際の試行で破綻が見えた箇所だけに最小限の定めを足す。

## 2. 歴史的経緯：第1版〜第5版の変遷と「引き算」の学び

### Phase 1：第1版〜第3版（2026-11-10〜11-16）— 工程の確立と過剰制約への気づき

[writing/rationale.md](https://github.com/mas256/doc-specs/blob/main/writing/rationale.md) には、初期の試行（小論文の試行や漸化式の教科書議論 [trials/zenkashiki-three-term.md](https://www.google.com/search?q=https://github.com/mas256/doc-specs/blob/main/trials/zenkashiki-three-term.md) 等）から得られた重要な教訓が記録されています。

* **壁打ち（工程0）と改稿（工程4）の新設（11-10〜11-11）**: 最初から構成や執筆に入ると芯が定まらないため、質問制限や承認待ちを外した「壁打ち」を独立させた。また `author-style.md` への移行や、既存原稿の改稿では要件定義書だけを必須とする整理を行った。

* **「一文一役」の単純強制を捨てた（11-11）**: 機械的に「一文に一つの役目だけ」を強制すると不自然になるため、「一文の役目は一つを基本としつつ例外条件を定める」形へ緩めた。

* **小論文試行を受けた修正（11-15〜16）**:

  * 「読後に期待すること」に構成案を書かせない（要件定義書の項目をそのまま節・段落の並びにすると硬直するため）。

  * 分量は「上限」として決め、上限まで無理に引き伸ばす目標にしない。

  * **執筆・草案段階での `{AI提案}`（`O3.9` / `M5.2の7`）を取り下げ**: 執筆中にAIが一歩踏み込んだ新提案を差し込むと流れが乱れるため、中身を広げる役目は前段の「壁打ち」へ移した。

### Phase 2：第4版から第5版への大転換（2026-11-17〜11-19）— 日本語悪化の原因究明と「外したもの」

第4版までの運用と [proposals/deletion-list-v5.md](https://www.google.com/search?q=https://github.com/mas256/doc-specs/blob/main/proposals/deletion-list-v5.md)（既存233規則の仕分け）等を経て、「ルールを細かく増やすほどAIの日本語が不自然になる」という課題が明確になり、第5版（[rationale.md](https://github.com/mas256/doc-specs/blob/main/rationale.md) / [DESIGN.md](https://github.com/mas256/doc-specs/blob/main/DESIGN.md)）では意図的な「引き算」が行われました。

#### 先祖返り禁止リスト（第5版で外したものと、その理由）

| 外した旧ルール・仕組み | 外した理由（なぜ害が出たか） | 第5版での置き換え | 
| ----- | ----- | ----- | 
| **構成案での字数・文面・言い回し固定** | 構成段階で表現や文字数まで縛ると、執筆時に不自然な詰め込みや引き伸ばしが起き、日本語が悪化する | 構成案は「段落ごとに何を言うか」を1行で書くのみ | 
| **既存文への直し圧縮** | 元の文を無理に短い枠へ押し込めようとして文脈が壊れる | 「削る → 言い換え → 足す」の自然な手順へ戻す | 
| **主軸としての反論の関門** | すべての文書に反論処理を必須にすると、不要な箇所まで防衛的な構成になる | 必要な論点として壁打ち・論点案で扱う | 
| **AIによる固定語・宣言文の勝手な決定** | AIが用語を勝手に固定して宣言文を書くと、依頼者の言葉遣いとズレる | 壁打ちで選び、宣言文は書かない | 
| **否定だけの品質基準** | 「〜しない」の禁止リストだけでは、何が良い文章なのかの指針にならない | 「よい日本語の5基準」と論理・表現の両面へ再編 | 
| **観点・題材の専門担当／検索の答え依存** | 担当を細分化しすぎると意図が分断される。また外部検索に結論を委ねると浅くなる | 企画・改稿・ロールモデルへ再編し、検索は「事実確認と視点増やし」のみに限定 | 

### Phase 3：第5版の集中点検とコミット履歴（2026-11-19〜11-20 / `0fe2dc9` 〜 `73fbd0e`）

[CURRENT.md](https://github.com/mas256/doc-specs/blob/main/CURRENT.md) および [main ブランチのコミット履歴](https://github.com/mas256/doc-specs/commits/main/)（216コミット）では、[handoff-2026-11-19/spec-review-opus5/report.md](https://www.google.com/search?q=https://github.com/mas256/doc-specs/blob/main/handoff-2026-11-19/spec-review-opus5/report.md) および [handoff-2026-11-20/spec-review-opus5-2/report.md](https://github.com/mas256/doc-specs/blob/main/handoff-2026-11-20/spec-review-opus5-2/report.md) を踏まえた細部の検証と重要な方針決定が行われました。

* **関わり方の連続化（点検1）**: 「全部AI任せ」「共同」「人が主」を固定モードにせず連続的な目安とし、最初の問いを「どれぐらいAIに任せたいか、自分でやりたい部分はどこか」に変更。

* **壁打ちの承認フロー廃止（点検2）**: 壁打ちに承認の関門を置くと発散が止まるため、状態値「議論中」を追加して自由な対話を保証。

* **台帳（`records/current.md`）の一本化とXMLタグ限定利用（`0fe2dc9` 等）**: 複数の引き継ぎメモを廃止し、暗黙の了解を防ぐため1行単位の台帳へ集約。XMLタグは「担当への入力・例・返却する台帳の行」という異種情報が混ざる境界にだけ使うことに決定。

* **基準環境を「ふつうの会話（無料版含む）」に置く（点検12・21）**: Claude Code や API を必須とせず、通常の単一チャットで窓口が担当になりきる運用を基準に据えた。

* **直し方の順と日本語基準の整理（`090df30`, `3114632` 等）**: 「削る → 言い換え → 足す」を書く側に戻し（足す・言い換えるときは文を分ける）、日本語の基準を「共通」と「好み」に分ける方針を決定。

* **点検11〜20番の決定（`f1539d8` 〜 `73fbd0e`）**: 選択肢の記号統一、承認の形の整理、質問の書き方などを確定。

## 3. 最近の議論で到達した構造的改善（第5版改訂の設計意図）

ここまでの歴史的経緯を踏まえたうえで、残っていた「文字数肥大化」「全体俯瞰の弱さ」「`author-style` の重さ」に対して導き出した設計意図は次の通りです。

### 3.1 「細部のエラー探し」と「骨格の組み直し」を物理的に分ける理由

* **なぜ従来の仕様では全体を見渡せなかったか**: 既存の仕様にも「論理のつながり・重複・飛躍を見る」規定はあったが、同じタスク内で語尾・表記・事実確認などの細部点検と並んでいたため、AIが答えを出しやすい**局所的なエラー探し**に意識を奪われていた。

* **解決の意図**: 「エラー探し」自体も重要である一方、それを骨格確定と混ぜない。本文の表現を視界から隠した「1行要約の並び（骨格）」だけを抜き出し、「別の並び・統合・削除案を1つ以上出す」独立ステップを全レイヤー（全体・構成案・読み直し・形式レビュー・仕様改訂）の**前段**に置くことで、自然に森を見てから木を直す流れを強制する。

### 3.2 要件定義書と `author-style.md` の境界・優先順位の意図

* **責務を分ける理由**: 現行の [author-style-template.md](https://www.google.com/search?q=https://github.com/mas256/doc-specs/blob/main/author-style-template.md) の第1部（文書の概要・読者像）は、文書ごとに作る要件定義書と重複・衝突する原因になっていた。要件定義書は「今回の文書（What / Who）」、[author-style.md](https://www.google.com/search?q=https://github.com/mas256/doc-specs/blob/main/author-style-template.md) は「著者固有の書き方（How）」と分離する。

* **なぜ「原則 `author-style` 優先」を覆さないのか**: 仮に「要件定義書 ＞ `author-style`」にすると、壁打ちのまとめでAIが書いた「読者に寄り添って親しみやすく」のような無難な一文が、著者の意図的な文体を上書きして「AIらしい普通の文章」に引き戻してしまう。そのため原則 `author-style` 優先を守り、今回だけ変えたい場合は明示タグまたは用途別の薄いファイルの切り替えで対応する。

### 3.3 「設定タスク」をなくす `author-style` 決定・育成の意図

* **なぜ202行テンプレートや架空の3択テストをやめるか**: 文章を書きたいユーザーに「12事項の質問」や「架空の例文の読み比べ」をさせると、本題と無関係な設定作業に時間を奪われストレスになる。

* **解決の意図**:

  * **70%の初期決定（執筆の入り口）**: 構成案が承認された直後に、AIが裏側の `parts/`（薄い索引＋80〜120字マイクロ見本）を組み合わせて「実際の本文の書き出し」を2〜3通り提示し、直感で1つ選んでもらう（そのまま本文冒頭になり、設定の手間感がない）。

  * **30%の育成（低負荷な差分学習）**: 全文の赤入れではなく、気になった1文の修正から `Before / After` 1行ペアを抽出し、「著者共通の好み（`author-style.md`）」と「この文書固有の約束（台帳）」に仕分ける。

  * **ロールモデル監査への渡し方**: 著者の意図したトーンを誤指摘しないよう `author-style.md` の型・ルール・NG例・見本は読ませる一方、細かい用語・表記表は読ませず、読者体験の監査に集中させる。

## 4. フラグシップモデルが判断に迷ったときの指針

1. **「ルールを足したくなったら、まず削るか・分離できないか考える」**: 文字数が増えれば `Sonnet` / `Haiku` の追従率は落ちる。プロンプトで言い聞かせるより、語尾や表記のような機械的チェックはツール（`trials/tools/endings.py` 等）や後段工程へ逃がす。

2. **「細部と骨格を混ぜない」**: どんなに正しいチェック項目でも、細部作業と並べれば細部に負ける。必ず視界を絞って「骨格の比較 → 細部のエラー探し」の順を保つ。

3. **「第4版以前の名残を残さない」**: `review/` の `base-v4.md` や旧参照が混在している状態は過渡期のものであり、第5版の統一基盤へ一本化する前提で扱う。

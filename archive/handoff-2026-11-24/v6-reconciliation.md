## 1 作業ファイルの置き場所の定め(依頼者の質問への答え)

- **main(第5版)**:handoff.md N5.4 にある。作業フォルダは依頼者が示す(標準は GitHub のリポジトリか Google Drive)。中は `author-style.md`、本文の版(`[文書名]-v1.md` …)、`records/`(`current.md` 台帳、`brief.md`、`points.md`、`outline.md`、`work/`)。完成稿の置き場所と、作業フォルダを指示書のフォルダのどこに置くかは定めていない。
- **v6**:handoff.md の第1節に、固定の形がある。`<project-name>/` の下に `README.md`、`final.md`(完成稿)、`records/`(`current.md`、`01-requirements.md`〜`05-review.md`、本文は `04-draft-v1.md` から版を重ねる)、`meta/`(`author-style.md` の写し、`sources/`)。GitHub に置けないときは zip にまとめる。
- **試行で守られたか**:main の試行(2026-11-20)は、どの会話も作業フォルダの位置をそれぞれに決めた(`kakurenbo/work/`、`kakurenbo-2019-waseda/` など)。v6 の試行も、固定の形どおりではない(hydrogen は `records/requirements.md`・`records/final.md`、sonnet は `essay.md` を一番上に置いた)。
- **リポジトリ(doc-specs)そのものの整理**:定めはない。外部のレビューは、草案(proposals/)と経緯(handoff-*/)を `archive/` へ、設計思想と改訂の記録を `docs/` へ移す案を出している。

## 4 v6 で、依頼者と議論していないまま変わったもの

- **要件定義書の七つの欄**:依頼者が承認した欄は「読者/読後に期待すること/立場/切り口/扱う内容/制約/資料」。v6 は「扱う内容」と「資料」を外し、「前提」と「この文書固有の用語」を足した。
- **担当の定義ファイルから、モデル・effort・道具の指定(先頭の `---` の部分)が消えた**。Claude Code では、このままではサブエージェントとして登録されない。モデルの方針(sonnet の high を最大に、haiku へ下げる)も、どこにも書かれていない。
- **形式のレビューが、ほぼ骨組みだけになった**(Lead の手順は数行)。依頼者は「review/ は求めたときに使うものとして残し、後で見直す」と決めていた。v6 の形では、レビューの回を一度も回せない見込み。
- **一文の長さ**:v6 は「一文を機械的に短く縛らない」と書く。依頼者の講評(opus の別の会話「頼っている、で切るべき」)と、共通の基準1(1文1主張)とぶつかるおそれがある。
- **author-style の書き出し選び(70%)と Before/After(30%)**、**削る担当を読んで直すに入れること**、**骨格から細部への三つの鉄則**:外部のレビューの案で、窓口の記録には依頼者の承認がない(code_artifact_1 に従って作ったとのことなので、方向は依頼者が選んだものと見ている)。

## 6 進み具合の見せ方(依頼者の案をもとにした窓口の案)

依頼者の例「工程: 点検の報告の処理 / 状態: 確認待ち / 質問：60%回答済み」をもとにした形。

```text
工程: 点検の報告の処理(31件中23件済み) / 状態: 確認待ち / 今回の質問: 3件
```

- 一つ目の括弧は、その工程の大きな単位(文書を作るときは段、点検のときは件)のうち、どこまで済んだか。
- 「今回の質問」は、この発言で答えてほしい数。
- 文書を作るときの例:「工程: 構成案の作成(5段のうち3段目) / 状態: 確認待ち / 今回の質問: 2件」。
